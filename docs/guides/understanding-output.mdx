Skylos keeps four questions separate: **Risk, Maintainability, Dead code,
Gate**. Finding tables provide the locations and evidence behind each readout.

## Read The Assessment

| Readout | Question | What it shows |
|---|---|---|
| **Risk** | What needs attention? | Highest unresolved severity and counts among correctness and risk findings. |
| **Maintainability** | How widespread is the friction? | Advice counts, affected units where measurable, and measured values against their limits. |
| **Dead code** | What may be removable? | Candidate counts, confidence and evidence to review before deletion. |
| **Gate** | What does our policy allow? | PASS or FAIL against configured limits when evaluated; otherwise not evaluated. |

New source scans do not average these into a numeric score or A–F grade.
One critical secret remains critical when the rest of the repository has no
findings, and adding unrelated code cannot dilute it. Correctness findings
from quality rules participate in Risk. Dead-code candidates have their own
readout and Advice contributes to Maintainability.

For example, a report can show **Risk: HIGH**, **Maintainability: 30 affected
Python functions out of 200 measured**, **Dead code: 4 candidates**, and
**Gate: PASS**. This means the configured gate permitted those findings; it
does not make the HIGH risk disappear. Review the findings and the actual
limits separately.

The independent `skylos debt` and `skylos defend` scores keep their own
contracts. Historical codebase grades describe the earlier scoring model;
they should not be compared with the new assessment as one continuous score.

### Spread And Excess

Maintainability reports measurements rather than an uncalibrated letter:

- **Spread:** 30 of 200 measured Python functions exceed a complexity limit:
  15%. The denominator contains only the eligible functions checked for that
  rule and language, not every line or language in the repository.
- **Excess:** complexity 11 against limit 10 is 1.1× the limit; complexity 45
  is 4.5×. The readout distinguishes an isolated small excess from a large one.
- A code unit is counted once within a rule when measuring spread, while
  every finding and its evidence remain available.
- When a rule has no complete unit inventory, Skylos shows its counts and an
  unavailable denominator. It does not invent a percentage. Language support
  and measurement depth vary; see [Language Support](/language-support).
- If no eligible functions were checked, the readout says so; it does not
  present a reassuring 0% or a 0/0 percentage.

Function inventories currently cover the following checks when quality
analysis completes:

| Language | Checks with function denominators |
|---|---|
| Python | Cyclomatic and cognitive complexity, nesting, argument count, function length |
| TypeScript / JavaScript | Cyclomatic complexity, nesting, argument count, function length |

Other rules and languages retain their counts and evidence, with unavailable
denominators where no matching inventory exists. Per-rule exclusions apply
to measurements too: TS/JS test callbacks excluded from the function-length
check are excluded from that denominator.

These proportions describe maintainability observations. They are not defect
probabilities, accuracy measurements or permission to refactor automatically.

### Coverage And Scope

Disabled checks are **not assessed**. Failed or unavailable checks are
**incomplete**. Known findings from completed checks remain visible when
another check fails. Zero findings only describes the checks and scope that
completed; it does not certify a repository safe.

Missing or unrecognized severities remain **Unknown**. When known urgent
findings coexist with unknown severities, Risk retains the known urgency and
discloses the unknown count.

The default `skylos .` checks dead code. It cannot give a clean Security or
Quality result for checks that were not enabled. Use `-a` for the main analyzer
families, or explicit flags for the checks you need.

Grouping, expansion and ordinary severity/category/file display filters do
not change the assessment or the gate. The readout discloses that it describes
all analyzed findings when a display filter hides rows. An exact rule selection
or a diff changes the findings scope and must not reuse a full-project assessment.

JSON and JSON-CI retain complete finding records for the chosen scope. New
source scans expose `assessment` version `1` instead of a new numeric `grade`.
Analysis errors and coverage limitations remain available alongside it.

## Finding Type And Severity

| Type | Meaning | Examples |
|---|---|---|
| **Defect** | A concrete correctness pattern that still needs contextual verification | Mutable defaults, blocking async calls, discarded async results |
| **Review** | A potential risk requiring context | Possible SSRF, dead-code candidates, unbounded ORM queries, unsafe type assertions |
| **Advice** | Maintainability or tooling conventions | Complexity, function length, duplicate literals, missing annotations |

Type describes the purpose of a check; severity describes impact. A **Review**
finding can be **CRITICAL**. Neither the label nor a confidence percentage
proves a production incident or authorizes a fix.

Terminal reports list Defect and Review individually, then group Advice by
rule with counts and affected files. All Advice remains visible by default.
Expand it when reviewing individual locations:

```bash
skylos . -a
skylos . -a --expand-advice
skylos . -a --format json -o report.json
```

MCP and deterministic LLM replies list Defect and Review in full and summarize
Advice by rule. MCP callers can request `expand_advice` or read the full saved
scan resource returned with the reply. JSON keeps every Advice record.
Advice still counts against applicable gate limits; grouping is not a gate
exemption. Existing code-health and architecture exemptions remain separate
policies; see [Quality Gate](/quality-gate).

Individual Rich rows use **Type, Severity, Rule, Message and Location**.
At narrow widths, severity or location can wrap into the Message cell. The
examples below show the evidence to look for within each finding family.

## Dead Code (default)

```
─────────────────── Unused Functions ───────────────────
 Type    Rule      Message                         Location
 Review  SKY-U001  old_handler; confidence 90%      app.py:16
 Review  SKY-U001  maybe_used; confidence 60%       utils.py:42
```

| Column | Meaning |
|--------|---------|
| **Type** | Dead-code candidates require Review before removal |
| **Rule** | The specific unused-code check, such as `SKY-U001` |
| **Name** | The unused function, import, class, or variable, shown in the message |
| **Location** | `file:line` where it's defined |
| **Conf** | Analyzer confidence (0–100%) based on static liveness signals; inspect the evidence before removing code |

**Confidence is a review signal:**

- **90–100%:** Higher-confidence candidate; inspect dynamic calls, public APIs
  and the evidence before deleting.
- **60–89%:** More uncertainty; review framework entrypoints, decorators and
  dynamic access such as `getattr`.
- **Below 60%:** Weaker static evidence; the configured threshold may omit it.

These are analyzer confidence values, not independently calibrated
probabilities that deletion is safe. A normal static scan does not run tests.

## Security (`--danger`)

```
───────────────────── Security Issues ─────────────────────
 Type    Severity  Rule      Message                          Location
 Review  CRITICAL  SKY-D211   SQL injection: tainted input     api/db.py:45
 Review  HIGH      SKY-D212   Command injection (shell=True)   utils/run.py:23
```

| Column | Meaning |
|--------|---------|
| **Type** | Whether the finding describes a Defect or needs contextual Review |
| **Rule** | The vulnerability check and rule ID, such as `SKY-D211` |
| **Severity** | Risk level: **Critical** > **High** > **Medium** > **Low** |
| **Message** | What was found and why it's dangerous |
| **Location** | `file:line` where the issue occurs |
| **Symbol** | The function or scope containing the vulnerable code, when supplied in the message |

## Reliability

Reliability findings describe release incompatibilities backed by evidence
across deployment, source, build, container, and target-contract files:

```text
Dockerfile:1  SKY-GPU001  reliability issue
deploy/rendered.yaml:42  SKY-DEP003  reliability issue
```

They are emitted under a separate top-level JSON bucket:

```json
{
  "reliability": [
    {
      "rule_id": "SKY-GPU001",
      "category": "RELIABILITY",
      "severity": "HIGH",
      "file": "Dockerfile",
      "line": 1,
      "message": "CUDA 12.4 requires NVIDIA driver branch 525 or newer.",
      "related_locations": [
        {
          "file": ".skylos/gpu-targets.yml",
          "line": 5
        }
      ]
    }
  ],
  "analysis_summary": {
    "reliability_count": 1
  }
}
```

`related_locations` records the other files and lines used to prove a
cross-file result. Diff-aware scans consider those supporting locations as
well as the primary location.

Reliability is activated by `--danger` / `-a`, or automatically when an exact
Reliability rule is requested with `--select`. `--category reliability` is a
display filter; it does not enable the analyzer by itself.

Reliability does not inflate `danger_count`. Its unresolved Defect or Review
findings participate in Risk without being relabelled as Security. Gates use
the independent `max_reliability` threshold, which defaults to `0`. See
[Release Reliability](../release-reliability) for the Kubernetes and GPU
contracts.

## AI Defects (`--ai-defects`)

In JSON output, AI-defect checks are grouped under `ai_defects`:

```json
{
  "ai_defects": [
    {
      "rule_id": "SKY-D224",
      "category": "ai_defect",
      "defect_type": "api_signature_hallucination",
      "message": "Installed API does not accept keyword argument 'imaginary_timeout'."
    }
  ],
  "analysis_summary": {
    "ai_defects_count": 1
  }
}
```

This bucket currently includes `SKY-A101`, `SKY-A102`, `SKY-A103`,
`SKY-A104`, `SKY-A105`, `SKY-L012`, `SKY-L023`, `SKY-D222`, `SKY-D224`, and
`SKY-D225`.
Grouping is category-based, not only prefix-based: historical `SKY-L` and
`SKY-D` IDs are kept for compatibility when their catalog category is
`ai_defect`.

`SKY-D223` remains a security/supply-chain finding because an undeclared but
real dependency is not a hallucination.

See [AI Defect Verification](../ai-defects) for the method, output contract,
and blocking posture.

## Secrets (`--secrets`)

```
──────────────────────── Secrets ────────────────────────
 Type    Severity  Rule      Message                        Location
 Review  CRITICAL  SKY-S101   AWS Access Key detected        config.py:12
 Review  CRITICAL  SKY-S101   Stripe Live Key detected       payments.py:8
```

| Column | Meaning |
|--------|---------|
| **Type** | Review the credential evidence without exposing its full value |
| **Provider** | The service the secret belongs to (e.g. AWS, Stripe, GitHub) or "generic" for high-entropy strings, supplied in the message |
| **Message** | Description of the detected credential |
| **Preview** | A masked snippet of the secret, supplied in the message |
| **Location** | `file:line` where the secret was found |

## Quality (`--quality`)

Advice is grouped by rule by default. With `--expand-advice`, individual
rows expose each measured value and location:

```
────────────────────────── Quality Issues ──────────────────────────
 Type    Rule      Message                         Location
 Advice  SKY-Q301  Complexity 18 (limit 10)         orders.py:45
 Advice  SKY-Q302  Nesting depth 6 (limit 3)        validators.py:23
 Advice  SKY-C304  Function 142 lines (limit 50)    reports.py:10
```

| Column | Meaning |
|--------|---------|
| **Type** | Defect, Review or Advice; separate from severity and check category |
| **Rule** | Complexity, Nesting, Structure, Logic, or another rule check |
| **Name** | The function, class, or string literal that triggered the finding, supplied in the message |
| **Detail** | The measured value and threshold, supplied in the message |
| **Location** | `file:line` where the finding starts |

**Understanding the Detail column:**

| Example | What it means |
|---------|--------------|
| `Complexity: 18 (max 10)` | Cyclomatic complexity is 18 independent paths against limit 10. Review the control flow and test cases |
| `Deep nesting: depth 6` | Code is 6 levels deep. Flatten with early returns or guard clauses |
| `Line count: 142, 142 lines` | Function is 142 lines long. Break into smaller functions |
| `repeated 12× (max 3)` | A string literal appears 12 times. Extract to a named constant |
| `Mutable default argument` | A logic issue like `def foo(x=[])` — no threshold, just a pattern violation |

## Dependency Vulnerabilities (`--sca`)

These findings are **Review** records. Their evidence includes the affected
package/version, vulnerability identifier, severity, reachability and fix:

```
────────── Dependency Vulnerabilities (SCA) ──────────
 #  Package             Vuln ID          Severity  Reachability    Message                Fix
 1  requests@2.28.0     CVE-2023-32681   High      Reachable       CRLF injection in...   2.31.0
 2  jinja2@3.1.2        CVE-2024-22195   Medium    Unreachable     XSS in templates...    3.1.3
```

| Column | Meaning |
|--------|---------|
| **Package** | The dependency and its installed version |
| **Vuln ID** | The CVE or advisory identifier |
| **Severity** | Risk level: Critical > High > Medium > Low |
| **Reachability** | Static evidence of a path to vulnerable code: **Reachable**, **Unreachable** in the analyzed graph, or **Inconclusive**. This is not proof of runtime exploitation or universal unreachability |
| **Fix** | The patched version to upgrade to |

## Circular Dependencies

Cycles are **Review** records. Their message contains the dependency chain,
cycle length and any suggested break point:

```
──────────────── Circular Dependencies ────────────────
 #  Cycle                          Length  Severity  Suggested Break
 1  auth → models → auth           2       MEDIUM    models
```

| Column | Meaning |
|--------|---------|
| **Cycle** | The chain of modules that import each other in a loop |
| **Length** | How many modules are in the cycle |
| **Severity** | Based on cycle length — longer cycles are harder to break |
| **Suggested Break** | The module to refactor to break the dependency loop |

## Tuning Thresholds

All quality thresholds are configurable in `pyproject.toml`:

```toml
[tool.skylos]
complexity = 10       # Max cyclomatic complexity
nesting = 3           # Max nesting depth
max_args = 5          # Max function arguments
max_lines = 50        # Max function length
duplicate_strings = 3 # Max times a string literal can repeat
```

See [Configuration](/cli-reference) for the full list of options.
