Skylos provides analysis capabilities for TypeScript (`.ts`, `.tsx`, `.mts`,
`.cts`) and JavaScript (`.js`, `.jsx`, `.mjs`, `.cjs`) files using tree-sitter
parsing.

## Features

TypeScript analysis includes:

- **Dead code detection:** Unused functions, classes, interfaces, enums, type aliases, variables, methods, imports, files (`SKY-E003`), and unnecessary exports (`SKY-E004`)
- **Security scanning:** `eval()`, unsafe `innerHTML`, `document.write()`, `new Function()`, `outerHTML`, string-based timers, command injection, webhook signature verification, Express and Next.js data flow, and client-side secret exposure
- **Quality analysis:** Cyclomatic complexity, nesting depth, function length, parameter count, a few logic checks, type-evidence bypasses, and compiler suppression directives

## How It Works

Skylos uses [tree-sitter](https://tree-sitter.github.io/) with the TypeScript grammar to parse files into a syntax tree. This enables accurate analysis without requiring a full TypeScript compiler setup.

### Parsing Pipeline

1. Read source file as bytes
2. Parse with tree-sitter TypeScript grammar
3. Query for definitions (functions, classes, interfaces, enums, type aliases, methods, variables, imports)
4. Query for references (calls, property accesses, type references, decorators, exports, inheritance)
5. Cross-reference to find unused definitions

## Dead Code Detection

### Supported Definitions

| Type | Detection Pattern |
|------|-------------------|
| Functions | `function foo() {}` |
| Arrow functions | `const foo = () => {}` |
| Classes | `class Foo {}` |
| Interfaces | `interface Foo {}` |
| Enums | `enum Foo {}` |
| Type aliases | `type Foo = ...` |
| Methods | `class { method() {} }` |
| Top-level variables | `const foo = value` |
| Imports | `import { foo } from '...'` |

### Export Awareness

Exported definitions are treated differently:

```typescript
// Not flagged - exported
export function publicApi() {}

// Flagged if not called internally
function internalHelper() {}
```

Two more rules look at files and exports, not single symbols:

- `SKY-E003` reports a TypeScript/JavaScript file that no other file imports
  and no entry point reaches.
- `SKY-E004` reports an `export` that nothing outside the file uses.

`--select SKY-E004` is rejected as an unknown rule ID today, even though the
finding is reported. Use `--category dead_code` or filter the JSON output
instead.

### Lifecycle Method Exclusions

Framework lifecycle methods are automatically excluded from dead code detection:

- **React:** `constructor`, `render`, `componentDidMount`, `componentWillUnmount`, `componentDidUpdate`, `shouldComponentUpdate`, `getDerivedStateFromProps`, `getSnapshotBeforeUpdate`
- **Angular:** `ngOnInit`, `ngOnDestroy`, `ngOnChanges`, `ngAfterViewInit`
- **Web Components:** `connectedCallback`, `disconnectedCallback`, `attributeChangedCallback`

### Reference Tracking

Skylos tracks references across many usage patterns:

- Function calls and `new` expressions
- Property accesses and member expressions
- Callback arguments, return values, and spread elements
- Array storage and object shorthand properties
- Type annotations and type references
- Decorator usage (decorated classes are not flagged)
- Export specifiers and `extends` clauses

## Security Rules

TypeScript and JavaScript findings use the shared `SKY-D` rule IDs. Run them
with `--danger` (or `-a`). See the [Rules Reference](/rules-reference) for the
full list, including Express and Next.js data-flow rules.

### SKY-D201: eval()

Detects use of `eval()`, which can execute arbitrary code.

```typescript
// Flagged (CRITICAL)
eval(userInput);
```

### SKY-D202: new Function() and string timers

Detects `new Function()` and `setTimeout()` / `setInterval()` with a string
argument. Each is equivalent to `eval()`.

```typescript
// Flagged (CRITICAL)
const fn = new Function('return ' + userInput);

// Flagged (HIGH)
setTimeout("alert('xss')", 1000);
setInterval("doStuff()", 500);

// Not flagged - function reference
setTimeout(() => alert('ok'), 1000);
```

### SKY-D226: innerHTML, outerHTML, document.write() and dangerouslySetInnerHTML

Detects HTML sinks that can enable XSS.

```typescript
// Flagged (HIGH)
element.innerHTML = userContent;
element.outerHTML = userContent;
document.write(data);
```

### SKY-D212: child_process command execution

Detects `exec()`-style calls on `child_process` (including aliased imports)
that may allow command injection. A regex `.exec()` is not flagged.

```typescript
// Flagged (HIGH)
child_process.exec(userCommand);

// Not flagged - regex exec is safe
const match = pattern.exec(input);
```

### SKY-D282: Unverified webhook handler

Detects Next.js, Express, and similar webhook handlers that process inbound provider events without obvious signature verification.

```typescript
// Flagged (HIGH)
export async function POST(req: Request) {
  const event = await req.json();
  await grantCredits(event.data.object.customer);
}

// Not flagged - provider signature is verified before trusting the event
export async function POST(req: Request) {
  const body = await req.text();
  const sig = req.headers.get("stripe-signature");
  const event = stripe.webhooks.constructEvent(body, sig, process.env.STRIPE_WEBHOOK_SECRET!);
}
```

The rule requires webhook/provider evidence, POST handling, and body usage, then suppresses when strong verification evidence such as `constructEvent`, `createHmac`, or `crypto.timingSafeEqual` is present.

### Other rules

TypeScript also reports prototype pollution through `__proto__` (`SKY-D510`),
`Math.random()` used for security values (`SKY-D250`), and client-side secret
exposure (`SKY-S102`) among others.

## Quality Rules

Run quality rules with `--quality` (or `-a`). TypeScript uses the same rule IDs
as Python for the shared checks.

### SKY-Q301: Function Complexity

Measures cyclomatic complexity for TypeScript functions.

**Complexity nodes:**

- `if_statement`
- `for_statement`
- `while_statement`
- `switch_case`
- `catch_clause`
- `ternary_expression`

```typescript
// Complexity: 4
function process(data: Data) {
  if (data.valid) {           // +1
    for (const item of data.items) {  // +1
      if (item.active) {      // +1
        handle(item);
      }
    }
  }
}
```

### SKY-Q302: Nesting Depth

Flags functions with deeply nested control flow.

**Nesting nodes:**

- `if_statement`
- `for_statement`, `for_in_statement`
- `while_statement`, `do_statement`
- `switch_statement`
- `try_statement`

```typescript
// Nesting depth: 3 (flagged if limit is 4)
function deep() {
  if (a) {                    // depth 1
    for (const x of items) {  // depth 2
      if (x.ok) {             // depth 3
        handle(x);
      }
    }
  }
}
```

### SKY-C304: Function Length

Flags functions that exceed the maximum line count.

```typescript
// Flagged if > 50 lines (default)
function longFunction() {
  // ... 60 lines of code
}
```

### SKY-C303: Parameter Count

Flags functions with too many parameters.

```typescript
// Flagged if > 5 parameters (default)
function configure(a: string, b: number, c: boolean, d: object, e: string[], f: Map<string, any>) {
  // ...
}
```

### Other quality rules

TypeScript also reports duplicate conditions in an if-else chain (`SKY-Q305`),
sequential `await` in a loop (`SKY-Q402`), and unreachable code (`SKY-UC002`),
plus the type-safety rules below.

### SKY-T103: Suspicious Chained Type Assertion

Reports a cast that reaches a precise type through the broad `any`, `unknown`,
`object`, or `{}` type.

```typescript
// Flagged
const user = input as unknown as User;

// Not flagged: validate the value instead
const user = UserSchema.parse(input);
```

### SKY-T104: TypeScript Compiler Suppression Directive

Reports effective `@ts-ignore` comments and file-wide `@ts-nocheck`. A narrow
`@ts-ignore` is MEDIUM severity; an effective `@ts-nocheck` is HIGH because it
disables checking for the whole file. `@ts-expect-error` is not reported.

```typescript
// Flagged
// @ts-ignore
const port: number = process.env.PORT;
```

### SKY-T105: Unvalidated JSON Type Assertion

Reports direct assertions from dynamic `JSON.parse()` data and from a proven,
awaited fetch `Response.json()` result.

```typescript
// Flagged
const user = JSON.parse(payload) as User;

// Not flagged: runtime validation establishes the type
const user = UserSchema.parse(JSON.parse(payload));
```

Skylos fails closed when the boundary cannot be proved. Shadowed or replaced
built-ins, mutated response methods, ambiguous aliases, generated files, and
TypeScript declaration files are not reported by these rules.

### Configuration

Override TypeScript thresholds separately from Python:

```toml
[tool.skylos.languages.typescript]
complexity = 15  # Higher threshold for TS
```

## Running Analysis

Skylos automatically detects TypeScript files in the scan path:

```bash
# Scans Python, TypeScript, and JavaScript
skylos ./src --danger --quality
```

### File Extensions

Supported extensions:

- `.ts`, `.mts`, `.cts` - TypeScript
- `.tsx` - TypeScript with JSX
- `.js`, `.mjs`, `.cjs` - JavaScript
- `.jsx` - JavaScript with JSX

`--format concise` prints one line per finding:

```bash
skylos . --danger --quality --format concise
```

## Monorepo And Import Resolution

Skylos discovers TypeScript and JavaScript workspaces from:

- `package.json` `workspaces` arrays and `{ "packages": [...] }` objects
- `pnpm-workspace.yaml` `packages` entries
- `lerna.json` `packages` entries
- `rush.json` `projects[].projectFolder` entries
- root `tsconfig.json` project references

Declared workspace packages are used for package-name import resolution. Skylos also resolves `tsconfig` `baseUrl`/`paths`, `extends`, package self-imports, package `exports`, package `imports`, `main`, `module`, and common source entrypoints such as `src/index.ts`, `src/index.tsx`, `index.js`, and `index.jsx`.

Workspace inventory is included in scan metadata so cloud uploads and JSON consumers can tell which packages were discovered, which files declared them, and whether undeclared package folders were found.

## Limitations

### Not Supported

- **Type checking:** Skylos doesn't validate TypeScript types
- **Full Node resolver emulation:** resolution covers common source and package metadata patterns, but not every conditional export or package-manager-specific edge case
- **JSDoc:** Documentation comments are not analyzed

### Workarounds

For React components that appear unused:

```typescript
// Components exported from index are often used externally
export { MyComponent } from './MyComponent';  // Not flagged
```

To silence one finding, put a Skylos comment on the same line:

```typescript
const handler = handlers[eventType]; // skylos: ignore
eval(trustedTemplate); // skylos: ignore[SKY-D201] reviewed: template is a constant
```

TypeScript and JavaScript accept `// skylos: ignore`, `// skylos: ignore[SKY-...]`,
`/* skylos: ignore */`, and `// skylos: ignore-start` ... `// skylos: ignore-end`.
`// noqa: skylos` and a bare `// noqa` do not work in these files. A
rule-scoped `skylos: ignore[SKY-U001]` does not hide dead-code findings; only
the blanket `// skylos: ignore` does. For an intentionally unused symbol, the
blanket form or `skylos whitelist` is the clear choice.

## Dependencies

TypeScript support requires:

```
tree-sitter>=0.25.2
tree-sitter-typescript>=0.23.2
```

These are installed automatically with Skylos:

```bash
pip install skylos
```

## Integration with Python Projects

Skylos can analyze mixed-language projects:

```
my-project/
├── backend/  # Python - fully analyzed
│   ├── api/
│   └── models/
├── frontend/  # TypeScript - analyzed
│   ├── src/
│   └── components/
└── pyproject.toml
```

```bash
# Analyze everything
skylos . --danger --quality

# Analyze only frontend
skylos ./frontend --quality
```
