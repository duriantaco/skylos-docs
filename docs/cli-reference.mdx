## Basic Usage

```bash
skylos <path> [options]
```

This form scans source code. The `<path>` argument can be a directory (scanned
recursively) or one file. A bare `skylos` or `skylos --help` opens the command
chooser; `skylos <path> --help` shows source-scan flags.

## Choose The Command By Its Input

Each command answers a different question. The source scan requires a path.

| Question | Command | Input Skylos reads |
|------|---------|--------------------|
| What problems are in this source tree? | `skylos <path>` | Source and project configuration; dead code by default, every main source analyzer with `-a` |
| How is this branch doing on Skylos Cloud? | `skylos cloud [PATH]` | Every main source analyzer, then the findings and this commit's Done receipt are uploaded and the branch's quality gate is printed with one link |
| Did the agent really finish this branch? | `skylos done --base main` | The branch's changes since its merge base with `main`: Skylos runs your tests (pytest automatically; other runners need `test_command` in `[tool.skylos.done]`) and compares the tests, test settings and CI steps with the base; writes a receipt to `.skylos/receipts/` |
| What does this change touch, and what should I read first? | `skylos done map --base main` | Each changed Python or TypeScript/JavaScript function since the merge base, with its old and new code, calls added and removed, its callers and removed security checks, sorted into read first, read, skim and skip (skip only when the logic is proven the same); computed from the code, so the same commit gives the same map |
| What AI-code mistakes are in this source? | `skylos verify [path]` | AI-defect checks over the selected file or tree, plus a separate Git HEAD behavior comparison for supported Python working changes |
| Should a model review static dead-code findings? | `skylos agent verify [path]` | LLM by default; optional [Jev-only or Jev-plus-LLM review](https://github.com/duriantaco/skylos/blob/main/docs/dead-code-review.md) |
| What do I tell my CTO? | `skylos report [path]` | Every main source analyzer locally, then one self-contained HTML page (or `--format md`): verdict, top five risks with fixes, issue counts, coverage gaps, scan date, commit and version |
| What does the combined repo report contain? | `skylos suite [DIRECTORY]` | Static analysis, technical debt, AI app safety, and provenance; local findings are report-only by default |
| Does an agent implementation have deployment guardrails? | `skylos defend [DIRECTORY]` | Recognized Python and TypeScript/JavaScript LLM integrations; gating requires a threshold flag or policy |
| What cleanup should I review next? | `skylos cleanup [path] --next` | Quality, AI-code and dead-code tasks, with local history and explicit preview/apply options; see [Cleanup](./cleanup) |
| Which Python dead code can Skylos remove? | `skylos clean [path] --dry-run` | Python import/function cleanup candidates; `--dry-run` never writes |
| Will this exact local GPU build fit the declared fleet? | `skylos preflight [ARTIFACT]` | A local built artifact plus `.skylos/gpu-targets.yml` or `.yaml`; OCI input is identity-only and returns `UNKNOWN` in the CLI |
| What vulnerabilities are in this container? | `skylos image scan IMAGE@sha256:<digest> --platform os/arch` | A remote registry image scanned through separately installed Trivy; `--fail-on` turns findings into a gate |

The three similarly placed checks have different inputs: `verify` scans source
and separately models supported Python working changes, `preflight` statically
inspects a local built GPU artifact, and `image scan` asks Trivy to inspect a
remote registry image. Bracketed paths on `verify`, `suite`, `defend`, and
`clean` default to the current directory. `suite` and `defend` require a
directory; `verify` and `clean` also accept a file. Run `skylos --help` for
this chooser, `skylos <command> --help` for one command, and `skylos commands`
for the installed command-family map.

### Gate, Exit, And Network Behavior

The report commands have different gate and network behavior:

- `image scan` requires Trivy on trusted `PATH` and uses Trivy's remote image
  source, so registry network access and any required registry credentials must
  already be available. Without `--fail-on`, a completed scan exits `0` even
  when it reports vulnerabilities.
- `suite` runs in the local process and does not upload unless `--upload` is
  set, but its dependency scan can query OSV. Findings are report-only: the
  command exits `0` regardless of their count. Operational and output failures
  are nonzero; `--upload` can also fail for an upload error or Cloud quality
  gate.
- `defend` reports guardrail findings by default. It becomes a gate with
  `--fail-on`, `--min-score`, or gate settings in an explicit policy.
- `cleanup` changes source only with `--apply`, and runs tests only with
  `--test-cmd`. A change stays `applied_unverified` when tests were skipped;
  see [Skylos Cleanup](#skylos-cleanup) for its exit codes.
- `clean` without `--dry-run` or `--apply` is interactive and can write after
  the final confirmation. Its current codemods support Python imports and
  functions. An apply pass still exits `0` if an individual edit prints a
  failure, so review the completion output.
- `done` exits `0` on pass, `1` when a blocking check fails or does not
  finish, and `2` when Skylos could not run (for example, the base is not
  fetched). It reads its settings from the base commit, so a change cannot
  loosen its own gate.

### `skylos init`

Initialize Skylos configuration in the current directory.
```bash
skylos init
```

Creates or appends a `[tool.skylos]` section to `pyproject.toml` with default
settings: thresholds, ignores, dead-code entrypoints, and vibe dictionary
extensions. See [Configuration](/configuration) for every key and for
`skylos.toml`.

### `skylos run` (removed)

`skylos run` exits with code `2`. Use `skylos . -a` for the main source audit
or `skylos suite` for the combined repository report.

### `skylos whitelist`

Manage the whitelist for suppressing false positives.
```bash
# Add a glob pattern
skylos whitelist 'handle_*'

# Add with reason (recommended for teams)
skylos whitelist my_func --reason "Called via registry lookup"

# View current whitelist
skylos whitelist --show
```

| Flag | Description |
|------|-------------|
| `--reason`, `-r` | Add reason/documentation for the whitelist entry |
| `--show`, `-s` | Display all current whitelist entries |

Patterns are saved to `[tool.skylos.whitelist]` in `pyproject.toml`.

### `skylos <path>`

Run static analysis on the specified path.
```bash
skylos . --danger --quality --ai-defects
```

### `skylos cloud [PATH] [scan flags]`

Scan `PATH` (default `.`) with every check (`-a`), show the findings, upload
them to Skylos Cloud, then show the quality gate for this branch and one link
to it.

```bash
skylos cloud                    # scan this repo and upload
skylos cloud --gate             # same, and exit 1 when the Cloud gate fails
skylos cloud --danger --secrets # run only these checks
skylos cloud src --exclude build
```

| Topic | Behavior |
|------|-------------|
| Checks | Every check (`-a`), unless you name some, e.g. `--danger --secrets` |
| Sends | Findings with file paths and code snippets of up to 7 lines (none for secrets), the branch, the commit, the git author email of each flagged line, and a map of your functions and classes (names, files, lines, sizes, which calls which). Not your repository |
| Done receipt | When the repository has a committed `[tool.skylos.done]` table (`skylos setup` writes it) and the working tree is clean, it also sends this commit's Done receipt, running `skylos done` first when there is none; the `Sent:` line says what reached Skylos Cloud. Uploads from a laptop are unverified until CI runs the workflow |
| First run | Opens your browser to log in and pick the project for this repo |
| Flags | The same scan flags as `skylos <path>` |
| Gate and exit code | Shows the Skylos Cloud quality gate: the project's policy in Skylos Cloud. Exit `0` even when it fails. Add `--gate` to exit `1` when it fails (use this in CI). `skylos . --gate` is a different, local gate: it uses `[tool.skylos.gate]` and uploads nothing |
| `--no-upload` | Refused with exit `2`: `skylos cloud` always uploads. Run `skylos .` for a local-only scan |
| No terminal and no login | Stops before scanning and exits `1` with "Not connected to Skylos Cloud. Run skylos login in a terminal, or set SKYLOS_TOKEN to a project token (create one in your project's Settings on skylos.dev)." In GitHub Actions or GitLab CI it uses the CI identity (OIDC) or `SKYLOS_TOKEN` |

`skylos cloud --help` prints this summary. `--upload` on a scan is the manual
form of `skylos cloud`: it uploads exactly the checks you picked. See
[Cloud Platform](/cloud#start-here-skylos-cloud) for example output.

### `skylos verify [path]`

Scan a file, directory, range, or stdin code blob for AI-code trust findings. Add
`--contract .skylos/ai-contract.yml` to enforce repo-specific generated-code
truth such as required route decorators or approved phantom-symbol checks. This
is the narrow in-loop verifier designed for coding agents and editor hooks, so
it returns only AI-specific findings instead of the full dead-code/security
report. In full scan JSON, AI-defect checks are grouped under `ai_defects`
rather than `quality` or `danger`.

```bash
# Verify one file
skylos verify src/app.py

# Verify only the edited range
skylos verify src/app.py --range 40:75

# Scan the project for context, then return findings for one file
skylos verify . --file src/app.py --range 40:75 --project-context

# Let an editor or agent send an unsaved buffer
printf '{"file":"src/app.py","code":"def handler(): pass\n","range":"1:1"}' \
  | skylos verify . --stdin --no-fail
```

For a directory target, the AI-defect analyzer scans that selected tree. Only
the separate Python `behavior` result compares working-tree functions with Git
HEAD; it does not narrow all analyzer findings to changed files. Path targets
enable dependency hallucination checks by default and may query public package
registries. Use `--no-dependency-hallucinations` to disable those lookups.

On a terminal, the command renders a human report. It emits versioned JSON with
`tool: "verify_change"` when stdout is redirected, when `--stdin` is used, or
to the file selected by `--output`. That result contains a `status`, target
file/range, and findings shaped for agent consumption:

```json
{
  "schema_version": 2,
  "tool": "verify_change",
  "status": "fail",
  "findings": [
    {
      "rule_id": "SKY-D224",
      "vibe_category": "api_signature_hallucination",
      "ai_likelihood": "high",
      "range": {
        "file": "src/app.py",
        "start_line": 42,
        "start_col": 0,
        "end_line": 42,
        "end_col": 0
      },
      "message": "Call uses an API shape that is not present in the installed package.",
      "suggested_fix": "Update the call to match the installed package API surface.",
      "confidence": 80,
      "severity": "HIGH",
      "category": "ai_defect"
    }
  ]
}
```

| Flag | Description |
|------|-------------|
| `--file <path>` | Target file when the positional path is a project root |
| `--range L1:L2` | Return findings that overlap a changed line range |
| `--stdin` | Read a JSON manifest with `file`, `code`, and optional `range` |
| `--project-context` | Scan the project path and filter to `--file` |
| `--dependency-hallucinations` | Include package metadata checks for hallucinated dependencies and versions |
| `--no-dependency-hallucinations` | Disable dependency checks and package-registry lookups |
| `--contract <path>` | Apply a specific AI hallucination contract |
| `--no-contract` | Disable contract discovery and application |
| `--exclude-folder <folder>` | Add an excluded folder. Can be repeated |
| `--confidence`, `-c` | Analyzer confidence threshold. Default: `60` |
| `--no-fail` | Exit `0` even when verify findings are returned |
| `--output`, `-o <file>` | Write JSON output to a file |
| `--diff REF` | **Source build:** verify changed lines since a Git baseline; an opted-in type check also compares diagnostic origins |
| `--type-check` | **Unreleased:** run the installed project checker with its real configuration |
| `--type-checker auto\|mypy\|pyright\|pyrefly\|tsc` | **Unreleased:** select the checker; requires `--type-check` |
| `--type-check-timeout SECONDS` | **Unreleased:** shared current/baseline checker budget, default `120`; requires `--type-check` |
| `--profile` | **Unreleased:** profile static verification; human summary goes to stderr and JSON contains `profiling` |
| `--profile-output <file>` | **Unreleased:** save the profile separately; also enables profiling |

Without `--no-fail`, `skylos verify` exits `1` for `fail` and `2` for
`incomplete`. An incomplete result means Skylos could not establish a requested
proof; it is not silently treated as a pass.

### `skylos done [path]`

Run the repository's tests and completion checks and write a receipt. Settings
come from the trusted baseline. `--base REF` compares against the merge base;
without it, Done compares uncommitted changes against HEAD.

```bash
skylos done --base main
```

`skylos done` compares the branch with its merge base and runs your tests. It
flags deleted or skipped tests, loosened test settings and CI test steps,
silenced lint or type checks, and code that special-cases the tests, advises
on code the branch left without callers, then writes a receipt to
`.skylos/receipts/`. It runs pytest automatically; other test runners need one
`test_command` line in `[tool.skylos.done]`.

Exit `0` on pass, `1` when a blocking check fails or does not finish, and `2`
when Skylos could not run (for example, the base is not fetched). It reads its
settings from the base commit, so a change cannot loosen its own gate. See the
[done gate guide](https://github.com/duriantaco/skylos/blob/main/docs/done-gate.md)
for every check and its limits.

The **unreleased source implementation** also supports installed project type
checking:

```bash
skylos done --base origin/main --type-check
skylos done --type-check --type-checker mypy
```

`--type-check` strengthens the type check to blocking. Its default is off;
trusted `[tool.skylos.done.checks]` policy can select `"block"` or `"advise"`.
`--no-tests` does not disable an enabled type check. Set the Done compiler
budget with `type_check_timeout_seconds` in trusted policy; the scan/verify
`--type-check-timeout` flag does not apply to Done.

See [Type Checking](./type-checking#enable-it-in-done-and-agent-stop-checks)
for configuration, diagnostic origins and incomplete comparisons.

### `skylos done map [path]`

Show what a change touches: each changed Python or TypeScript/JavaScript
function, method and class with its old and new code, calls added and
removed, its callers and whether they were updated, removed security
checks, breaking or compatible signature changes, and what to read first,
read, skim or skip. Skip holds only changes whose logic is proven the same.
The map is computed from the code, not by a model, and makes no network
requests. See [Change Map](/change-map) and the
[Agent Code Workflow](/workflow).

```bash
skylos done map                          # uncommitted changes, compared with HEAD
skylos done map --base origin/main       # a pull request, compared with its merge base
skylos done map --format json            # for a review agent or script
skylos done --base origin/main --map     # the done verdict, then the map
```

| Flag | Description |
|------|-------------|
| `--base <ref>` | Compare with the merge base of this ref. Default: `HEAD` (uncommitted changes only) |
| `--format text\|json\|markdown` | Output format. Default: `text` |

Exit `0` when the map is shown and `2` when it cannot be built, for example
when the base ref does not exist. The map has no verdict. `skylos done --map`
prints it after the done verdict and never changes the verdict, receipt or
exit code.

### `skylos setup [path]` and `skylos open [path]`

```bash
skylos setup                 # once per repository; safe to run again
skylos setup --no-ci         # skip the PR check
skylos setup --no-codex      # leave Codex settings alone
skylos open                  # compare with origin/HEAD (else main or master)
skylos open --base origin/develop
```

`skylos setup` writes a block between `skylos:start` and `skylos:end` markers in

Codex agent hooks (`.claude/settings.json`, `.codex/hooks.json`), writes the
`[tool.skylos.done]` table so Done can run your tests, writes the PR check with
`skylos cicd init` and builds the code map. It warns when your PATH or Codex
points at a different Skylos. `skylos open` is `skylos graph open` with the base
detected; its Check this change button runs `skylos done` and refreshes the
Changes and Pipeline tabs. Walkthrough: [Tutorial](/workflow).

### `skylos graph [path]`

Map every Python and TypeScript/JavaScript function, method and class (and Go, Java, Rust and PHP as a first pass, with calls matched by name): what
calls what, which tests reach it, the answers those tests expect, and what
each one does in plain English. With `--since`, every changed function gets a
verdict, and "same logic" is shown only when it is proven. See
[Codebase Graph](/graph).

```bash
skylos graph                              # build .skylos/graph/, compare with HEAD
skylos graph open                         # local browser view (127.0.0.1 only)
skylos graph --since origin/main          # mark everything this branch changed
skylos graph show load_config --format json
skylos graph impact load_config
skylos graph describe                     # plain-English descriptions, your model key
skylos graph describe --via skylos        # Skylos writes them for credits (not live in Skylos Cloud yet)
skylos graph --since origin/main --upload # logic-change report to Skylos Cloud (not live in Skylos Cloud yet)
```

| Subcommand or flag | Description |
|------|-------------|
| `--since <ref>` | Compare with this ref and give each changed function a verdict. Default: `HEAD`; `none` skips it |
| `--format text\|json` | Output format. Default: `text` |
| `--upload` | Send the logic-change report to Skylos Cloud (not live in Skylos Cloud yet). Needs committed changes and `skylos login` or CI; the project must have Logic changes reports turned on (1 credit per pull request) |
| `open` | Build and open the local viewer; rebuilds when files change |
| `show NAME` / `find QUERY` / `impact NAME` | One function's card, a name search, everything that depends on it |
| `areas [ID]` | The codebase split into areas that work together, or one area's members |
| `relevant FILE...` | The code that matters most to these files, within `--budget` tokens (default 2,000) |
| `changes --base <ref>` | Changed functions with verdicts and evidence, in read first, read, skim and skip sections |
| `describe` | Plain-English descriptions with your own model key. `--via skylos` (not live in Skylos Cloud yet) uses Skylos's key: 1 credit per 100 functions, or per 20 changes with `--changes` |
| `pending` / `import FILE` | Let your coding agent write the descriptions. `pending --changes --base <ref>` lists changed code to explain |
| `report --base <ref>` | Build the report Skylos Cloud stores: verdicts and reasons, no source code |

Building the graph runs none of the project's code and makes no network
requests. Only `describe` (your key or `--via skylos`) and `--upload` send
anything.

### `skylos preflight [ARTIFACT]`

Check one exact local built GPU artifact against the machines declared in
`.skylos/gpu-targets.yml` (or `.yaml`). This command inspects artifact evidence.
It does not review source edits or scan packages for CVEs.

```yaml title=".skylos/gpu-targets.yml"
version: 1
targets:
  - name: inference-t4
    vendor: nvidia
    driver: "535.104.05"
    compute_capability: "7.5"
    platform: "linux/amd64"
```

Inspect a local file or directory:

```bash
skylos preflight build/app
```

Local version-1 inspection supports Linux ELF/CUDA artifacts and requires a
trusted NVIDIA `cuobjdump` installed outside the project and artifact. Skylos
takes private file snapshots and never loads or executes target code.

You may omit `ARTIFACT` when `.skylos/release.json` names one project-relative
artifact:

```json title=".skylos/release.json"
{"version": 1, "artifact": "build/app"}
```

There are no preflight mode flags. The artifact and fleet contract define the
check. A valid report is concise on a TTY and schema-version-1 JSON when stdout
is redirected. Argument and adapter errors can be plain text and exit `2`.

| Status | Exit | Meaning |
|------|:----:|---------|
| `PASS` | `0` | The exact identity and every fleet target pass all checks within the declared static scope |
| `FAIL` | `1` | Artifact evidence proves at least one fleet target incompatible |
| `UNKNOWN` | `2` | Evidence is missing, ambiguous, unsupported, incomplete, or input is invalid |

A digest-pinned OCI reference is accepted as an identity, but this CLI never
pulls or starts it and therefore returns `UNKNOWN`. A trusted library caller
can supply digest-bound inspection facts to `skylos.preflight.run_preflight`.

Version 1 covers exact local identity, Linux ELF platform, selected executable
fatbin architecture routes, a static packaged `$ORIGIN` CUDA runtime route,
and documented driver-family compatibility. It does not establish runtime
execution, workload correctness, memory demand, performance, nonselected or
relocatable fatbins, per-kernel symbol parity, or Windows PE runtime imports.
See [Release Reliability](./release-reliability#built-artifact-preflight) for
the evidence model and library API.

Here, a *selected executable fatbin* is the executable CUDA record set that
`cuobjdump --list-elf`/`--list-ptx` selects. Its *producer identifier* groups
the cubin and PTX records that must share a compatibility route. Every observed
group needs native cubin coverage for `PASS`; PTX-only coverage remains
`UNKNOWN` because static inspection does not prove the deployment driver's JIT
path. Across checks and targets, `FAIL` wins over `UNKNOWN`, and `UNKNOWN` wins
over `PASS`.

### `skylos image scan`

Scan a digest-pinned remote registry image for package vulnerabilities. Install
Trivy separately as a trusted executable on `PATH`, and provide registry
network access and any required registry credentials:

```bash
skylos image scan IMAGE@sha256:<digest> \
  --platform linux/amd64 --fail-on high
```

This command checks CVEs. It does not check CUDA architectures, packaged CUDA
runtime binding, or fleet driver compatibility; use `skylos preflight` for
those artifact checks.

Without `--fail-on`, vulnerability findings are report-only and a completed
scan exits `0`. With `--fail-on LEVEL`, findings at or above that severity exit
`1`. Scanner or report incompleteness exits `2`.

To convert an existing Trivy image vulnerability report instead of scanning,
use `skylos ingest trivy --input trivy.json --sarif image.sarif`. See
[Container-image scanning](https://github.com/duriantaco/skylos/blob/main/docs/container-image-reports.md#import-an-existing-trivy-report).

### `skylos defend [DIRECTORY]`

Findings are report-only and exit `0` unless `--fail-on`, `--min-score`, or an

an unsupported or unrecognized implementation has guardrails.

## Finding Filters

| Flag | Description |
|------|-------------|
| `--severity LEVEL` | Show findings at or above `critical`, `high`, `medium`, or `low` |
| `--category CAT` | Show one or more comma-separated categories: `security`, `reliability`, `secret`, `quality`, `ai_defects`, `dead_code`, or `dependency` |

## Type Checking And Profiling (Unreleased)

These options require the unreleased source implementation. Use the help in
your installed build to check availability.

```bash
skylos . --type-check --type-checker mypy
skylos . --diff origin/main --type-check
skylos verify src/app.py --type-check --profile
skylos . --format json --profile-output profile.json > findings.json
```

| Flag | Behavior |
|------|----------|
| `--type-check` | Execute installed mypy, Pyright, Pyrefly or `tsc` with project configuration. Configured plugins can execute; use a trusted repository |
| `--type-checker auto\|mypy\|pyright\|pyrefly\|tsc` | Select a configured checker. Multiple configured tools require an explicit choice. Requires `--type-check` |
| `--type-check-timeout SECONDS` | Shared current/baseline checker budget for scans and `verify`; default `120`, greater than `0` and at most `3600`. Requires `--type-check` |
| `--profile` | Measure Skylos's static scanner phases, Python functions and call counts. Does not enable checker, application or test execution |
| `--profile-output <file>` | Write standalone profiling JSON; enables profiling. Parent directory must exist; use a different path from `--output` |

Compiler diagnostics appear in `type_check`, separate from Skylos rule findings.
Without a baseline, current type errors block. With a comparable Git baseline,
confirmed preexisting errors remain visible; introduced or unclassified errors
block. A missing checker, unsupported comparison or checker failure is
incomplete. Scans and `verify` exit `1` for type failures and `2` for an
incomplete requested check; scan `--force` can override type failures, and
`verify --no-fail` keeps its explicit override.

Profiling adds a human summary on stderr and a `profiling` object to JSON scan
and verify reports. Profile output failures are operational errors (exit `2`)
even with `--force`. The compiler's separate time is `type_check.seconds`;
`--profile` does not profile its subprocess.

See [Type Checking](./type-checking) and [Analysis Profiling](./profiling) for
baseline requirements, completion limits and the profile schema.

## Reference Graph Cache

Skylos has a persistent reference graph cache format at:

```text
.skylos/index/v1/reference_graph.json
```

The cache stores file signatures, definitions, references, imports, and reverse
dependencies keyed by content hash. Index-aware verifier and agent paths can
reuse unchanged graph entries and conservatively invalidate changed files plus
their direct dependents.

You should normally gitignore `.skylos/index/`. It is safe to delete; Skylos will
rebuild cache payloads when an index-aware path writes them again. The cache does
not index symlinks, non-regular files, or very large source files.

## Diff Filtering

| Flag | Description |
|------|-------------|
| `--diff [BASE_REF]` | Only report findings in lines changed since BASE_REF (e.g. `--diff origin/main`). Use `--diff` without a value to compare with the pull request's target branch on GitHub Actions, GitLab CI, Jenkins, Bitbucket Pipelines, Azure Pipelines, Buildkite, Travis CI, Drone and Woodpecker, else `origin/main`; see [Other CI Providers](/ci-cd#other-ci-providers). Unlike `--diff-base` which filters at the file level, `--diff` uses unified diff hunk headers for exact line-range matching. |
| `--diff-base <ref>` | *(File-level)* Only report findings in files changed since the given ref. |

**Example:**
```bash
# Only show findings in lines your PR touched
skylos . --diff origin/main --danger --quality --ai-defects

# Compare with the pull request's target branch (detected per CI), else origin/main
skylos . --diff --danger --secrets --quality --ai-defects
```

For cross-file findings, Skylos also checks `related_locations` against the
changed scope. A finding can therefore remain visible when the PR changes a
supporting contract, manifest, source route, build file, or Dockerfile rather
than only the finding's primary location. Required fail-closed prerequisites
such as `SKY-GPU000` are retained for selected leaf rules.

Agent-config and publish-job findings (`SKY-D365` to `SKY-D377`) are judged
differently. With `--diff`, one is new when the merge base did not have the
same finding (rule, file, event or job name and command), even if its line
did not change; with `--diff-base` alone, every such finding in a changed
file counts. See
[How They Count In The Gate](./supply-chain#how-they-count-in-the-gate).

## Skylos Cleanup

`skylos cleanup` combines existing detector evidence with a prioritized queue,
local history, named plans and limited deterministic edits. The default scan leaves source unchanged. Preview a patch
for a selected task, then explicitly apply it and request the relevant tests:

```bash
skylos cleanup . --top 5
skylos cleanup . --next
skylos cleanup . --diff origin/main --context
skylos cleanup . --task TASK_ID
skylos cleanup . --task TASK_ID --apply --test-cmd "pytest -q test/test_orders.py"
skylos cleanup . --defer TASK_ID --reason "Review public callers first"
skylos cleanup . --restore TASK_ID
skylos cleanup . --history --format json
```

| Flag | Description |
|------|-------------|
| `--format human` / `--format json` | Human output by default, or machine-readable JSON |
| `--top N` | Positive display limit for each queue; default `10` |
| `--all-advice` | Include optional maintainability advice |
| `--diff BASE` | Scan the full Git project and display tasks in changed files; does not prove each finding is new |
| `--from-report REPORT` | Reuse analyzer JSON without rescanning; supply the original scan root as the path |
| `--next` | Show the next open task, or advice when no task is available |
| `--task ID` | Preview a supported deterministic patch; a unique task-ID prefix is accepted |
| `--apply` | Apply the selected patch and statically rescan; requires `--task` |
| `--test-cmd COMMAND` | Explicitly authorize this test command after applying; no shell interpretation |
| `--junit-report PATH` | Read the authorized runner's fresh project-relative JUnit report; pytest produces one automatically |
| `--defer ID --reason TEXT` | Defer local work without changing raw findings or gate policy |
| `--restore ID` | Return deferred work to the open queue |
| `--history` | Read local cleanup history without scanning |
| `--no-state` | Disable reading and writing cleanup history |
| `--create-plan NAME --plan-task ID` | Create an ordered local plan; repeat `--plan-task` for Python anchored tasks |
| `--prerequisite TEXT`, `--acceptance-check TEXT` | Store plan requirements as text; never executes them |
| `--plan NAME`, `--plans` | Inspect one plan or list local plans |
| `--move-task ID --before ID` | Reorder work in the selected plan |
| `--complete-task ID --note TEXT` | Record manual, unverified completion; stale steps require a note |
| `--context` | Add bounded source lines, static graph impact, candidate callers and suggested test files |
| `--review` | Send bounded context to the configured model for separately labeled advice |
| `--reviews` | Read saved cited advice with current/stale source status |
| `--promote-review ID` | Explicitly add current saved advice to the selected plan, retaining its advice label |
| `--model`, `--provider`, `--base-url` | Configure the optional model review |

`ready` means work exists; `clear` means no visible work in the recorded scope.
Both exit `0`. Execution reports `verified` only when fresh observed tests
pass and a complete comparable rescan removes the target without new defects
or high-severity review findings. Skipped tests leave `applied_unverified`.
Unavailable checks produce `incomplete` and exit `2`; invalid input also exits
`2`. Failed checks exit `1` and attempt rollback while preserving intervening
file changes. Read the test, rescan and rollback receipts. These are recorded
checks, not universal behavioral proof or a security verdict.
An opaque exit zero is insufficient: tests must be observed through fresh JUnit
results. Test count and whether changed code was exercised remain separate.
Apply scans check security/secrets as well as quality/AI-code/dead code; they do
not enable dependency registry checks.

Edits support conservative Python `SKY-U001`, `SKY-U002` and `SKY-L038` cases,
plus a narrow TypeScript/TSX same-directory singleton named `import type`
removal. Unsupported or ambiguous cases require manual review; no compiler or
package script runs by default. Named plans currently require Python anchors.
Local history is
stored in `.skylos/cache/cleanup.json`; absence becomes `not_reported`, not a
verified fix. Saved reports cannot authorize edits, model review or history
changes. `--review` is separate from patch application and requires the LLM
extra and provider configuration. See [Cleanup](./cleanup) for the full workflow.
Saved reviews retain citations, model/provider and source hashes unless
`--no-state` is selected. Advice never authorizes edits or verifies a fix.
Check installed `skylos cleanup --help`: new options describe current source and
may not yet be in your packaged release.

The separate `skylos clean` command below retains its Python dead-code workflow.

## Deterministic Cleanup

Use `skylos clean` for Python import and function cleanup. With no mode flag it
asks about each candidate and can write files after final confirmation.
`--dry-run` is the guaranteed no-write preview.

```bash
# Preview Python import/function cleanup edits without writing files
skylos clean . --dry-run --types import,function --confidence 80

# Apply the same kind of cleanup without prompting
skylos clean . --apply --types imports --confidence 80

# Comment out matches instead of removing them
skylos clean . --apply --comment-out --types import,function --confidence 80
```

| Flag | Description |
|------|-------------|
| `--dry-run` | Print planned edits and write nothing |
| `--apply` | Apply matching cleanup edits without prompting |
| `--confidence <N>` | Minimum finding confidence; defaults to `80` in noninteractive mode |
| `--types <list>` | Comma-separated cleanup types; currently `import` and `function` |
| `--comment-out` | Comment out matches instead of deleting them |

`skylos clean` uses Python LibCST codemods and path-containment checks.
Automatic cleanup currently edits unused imports and unused functions only;
classes, variables, other languages, and lower-confidence findings remain
review items. The command currently exits `0` after a completed apply pass even
if an individual transform failure was printed, so review the completion
output.

## CI/CD Commands

### `skylos cicd init`

Set up the pull request gate for the CI your repository uses. On GitHub
Actions it generates a workflow with a PR quality gate, a Done job when tests
are discovered, and a default-branch Cloud upload through GitHub OIDC. On
GitLab CI, Jenkins, Bitbucket Pipelines, Azure Pipelines and CircleCI it
writes that CI's file, or prints the block to add when the file already
exists; see [Other CI Providers](/ci-cd#other-ci-providers). CIs other than
GitHub Actions need Skylos 5.1.0 or newer.

The behavior and options in this section require **Skylos 4.46.0 or newer**.
Skylos 4.45.0 has the older generator and does not accept `--no-upload`,
`--done` or `--default-branch`.

```bash
python -m pip install --upgrade "skylos>=4.46.0"
skylos cicd init
skylos cicd init --no-upload
```

PR scan and Done jobs have no Cloud credentials or OIDC permission. The
separate upload job runs only on default-branch pushes and needs the Skylos
GitHub App installed on the repository. Inspect the generated test dependency
step before making **Skylos Done** a required check.

| Flag | Default | Description |
|------|---------|-------------|
| `--ci` | detected | CI to set up: `github`, `gitlab`, `jenkins`, `bitbucket`, `azure`, `circleci`, or `other` (prints the commands to add). |
| `--python-version` | 3.12 | Python version for the workflow |
| `--triggers` | `pull_request push` | GitHub event triggers |
| `--analysis` | `dead-code security quality ai-defects secrets dependency` | Analysis types to enable |
| `--no-baseline` | false | Skip baseline comparison |
| `--llm` | false | Include LLM-enhanced analysis |
| `--model` | — | LLM model to use with `--llm` |
| `--claude-security` | false | Add a parallel Claude Code Security scan job. |
| `--upload` / `--no-upload` | on for GitHub Actions | Upload full scans on default-branch pushes with GitHub OIDC; no stored API key required. Use `--no-upload` for CI without Cloud. Other CIs get no upload job. |
| `--done` / `--no-done` | auto | Add Done when pytest tests or a configured `[tool.skylos.done]` test command are found; force or omit the job explicitly. |
| `--default-branch` | `origin/HEAD`, else `main` and `master` | GitHub Actions: the branch whose pushes upload. CircleCI and other CIs: the branch the gate compares with (`origin/HEAD`, else `main`). |
| `--scan-path` | `.` | Directory to scan, such as `apps/api`. Does not route the generated policy-sync step to a Cloud project subpath. |
| `--risk-review` | false | Add the **Skylos risk review** job. It fails while a pull request has risks, such as deleted tests or removed auth, that no person with write access approved. Bot approvals do not count. |
| `--advisory-gate` | false | Report quality-gate failures without failing the generated gate job. |
| `--defend` | false | Include AI Defense checks. |
| `--output`, `-o` | the CI's own file | Output file path, for example `.github/workflows/skylos.yml` or `Jenkinsfile` |
| `--force` | false | Replace an existing GitHub workflow without asking. The old file is kept next to it as `<name>.bak`. |

`--llm`, `--model`, `--claude-security`, `--defend`, `--risk-review`,
`--advisory-gate`, `--done`/`--no-done`, `--triggers` and `--force` apply to
GitHub Actions only. On other CIs, Skylos says which of them were not used.

For multiple Cloud projects in a monorepo, use the GitHub App's generated
per-root workflow. The CLI-generated `skylos sync pull` step sends no GitHub
project-subpath header, so `--scan-path` alone can leave policy sync ambiguous.

## Runtime Analysis

| Flag | Description |
|------|-------------|
| `--trace` | Run pytest with `sys.settrace()` to record all function calls, reducing false positives from dynamic code |

### When to Use `--trace`

Use `--trace` when static analysis flags code you know is used:

- **Visitor patterns** (`visit_FunctionDef` called via `getattr`)
- **Plugin hooks** (`pytest_configure`, `pytest_addoption`)
- **Dynamic dispatch** (`getattr(obj, method_name)()`)
```bash
skylos . --trace
```

:::note
The `.skylos_trace` file is saved in your project root. Commit it to skip re-running tests on subsequent scans.
:::

## Quality Gate
```bash
skylos <path> --gate [command...]
```

| Flag | Description |
|------|-------------|
| `--gate` | Run as a quality gate. Blocks if thresholds for the enabled or selected analyzers are exceeded. |

Reliability is evaluated separately from Security and defaults to
`max_reliability = 0`. A bare `--gate` does not enable every analyzer; combine
it with explicit analysis flags or exact `--select` rules. If the gate passes,
Skylos either runs the provided command or launches the deployment wizard. If
the gate fails, it shows reasons and (unless `strict = true`) offers a bypass
prompt.

**Example:**
```bash
skylos . --danger --secrets --quality --ai-defects --gate

# Targeted GPU release gate; SKY-GPU000 is retained automatically
skylos . --select SKY-GPU001,SKY-GPU002,SKY-GPU003 --gate
```

## Exit Codes

Exact meaning is command-specific; these are the common categories:

| Code | Meaning |
|------|---------|
| `0` | Command-specific success; report-only commands can still contain findings |
| `1` | Findings, a gate/policy decision, or another command-specific analysis or operational failure caused the command to fail |
| `2` | The invocation, configuration, or input was invalid, or the command could not produce a usable result safely |

For example, `skylos compare` uses `0` for a usable receipt and `2` for an
invalid, unsafe, or unusable comparison; it does not use `1`. See
[Scanner Comparison](./scanner-comparison#exit-codes).
