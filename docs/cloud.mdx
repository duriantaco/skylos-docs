Skylos is local-first. The CLI does the analysis on your machine or in CI. **Skylos Cloud** is the hosted layer that stores scan results, applies shared project policy, tracks issues over time, and gives your team one place to review and act.

## Start Here: `skylos cloud`

To use Skylos Cloud, you need one command:

```bash
skylos cloud
```

`skylos cloud` runs every check (`-a`), shows the findings, uploads them to
Skylos Cloud, then prints this branch's quality gate and one link to it.

- First run: it opens your browser to log in and pick the project for this repo.
- Checks: every check (`-a`), unless you name some.
  `skylos cloud --danger --secrets` runs only those.
- Sends: findings with file paths and code snippets of up to 7 lines (none for
  secrets), the branch, the commit, the git author email of each flagged line,
  and a map of your functions and classes (names, files, lines, sizes, which
  calls which). Not your repository.
- Exit code: 0 even when the gate fails. Add `--gate` to exit 1 on a failed
  gate (use this in CI).
- Takes the same scan flags as `skylos .`, e.g. `skylos cloud src --exclude build`.
- No terminal and no login: it stops before scanning and exits 1 with
  "Not connected to Skylos Cloud. Run skylos login in a terminal, or set
  SKYLOS_TOKEN to a project token (create one in your project's Settings on
  skylos.dev)." In GitHub Actions or GitLab CI it uses the CI identity (OIDC)
  or `SKYLOS_TOKEN`.

### What You See

`skylos cloud` prints the findings tables, like `skylos . -a`, then the gate
for this branch.

Failed gate on a branch:

```text
✗ Quality gate on feat/login: FAILED (was PASSED on 24 Oct 15:38 UTC, 1ba9895) · 1 critical security issue
  Open: https://skylos.dev/dashboard/projects/<project>?branch=feat%2Flogin
  Next: fix the issues behind the failed gate, then run skylos cloud again.
```

The issues are in the findings tables printed above these lines.

Passed gate on main, no CI yet:

```text
✓ Quality gate on main: PASSED (was FAILED on 24 Oct 15:38 UTC, 1ba9895)
  Open: https://skylos.dev/dashboard/projects/<project>
  Next: skylos cicd init — adds a Skylos check to every pull request.
```

When you upload `main` from your laptop with your `skylos login` token, one
more line says the upload is unverified: it is shown in Skylos Cloud but does
not set the project verdict or mark issues fixed.

The link opens the project Overview for that branch: the gate, why it failed,
and how it changed since the last run.

### Use It In CI

```bash
skylos cloud --gate
```

`--gate` makes the command exit 1 when the Skylos Cloud gate fails, so the CI
job fails too. That gate is your project's policy in Skylos Cloud.
`skylos . --gate` is a different, local gate: it uses the limits in your
`[tool.skylos.gate]` config and uploads nothing.

Set `SKYLOS_TOKEN` to a project token in CI systems without OIDC. In the
project's Settings, select **Mark for CI** on that token. Uploads with an
unmarked token are unverified: they show in Skylos Cloud, but they don't
publish a check or mark issues fixed. Never mark a token that is on a
developer machine.

Skylos Cloud does not accept GitHub OIDC uploads from ordinary `pull_request`
jobs. For a check on every GitHub pull request, use the workflow from
`skylos cicd init`. See [CI/CD Integration](/ci-cd).

### The Manual Form: `--upload`

```bash
skylos . --danger --secrets --upload
```

`--upload` on a scan is the manual form of `skylos cloud`: it uploads exactly
the checks you picked.

## Which Commands Talk To Skylos Cloud

You only need `skylos cloud`. The rest are for control:

| Command | Use it to |
|:---|:---|
| `skylos cloud` | scan, upload, see the gate (the one to remember) |
| `skylos login` | switch to another project |
| `skylos whoami` | see which account and project you are connected to |
| `skylos project <command>` | manage the project linked to this repo |
| `skylos upload --retry` | resend uploads that did not finish |
| `skylos sync` | pull the project's Cloud policy into the repo |
| `skylos credits` | check your credit balance |
| `--upload` on a scan | the manual form of `skylos cloud`: uploads exactly the checks you picked |

Scans never upload unless you run `skylos cloud` or add `--upload`. For every
network request the CLI can make, see
[What leaves your machine](https://github.com/duriantaco/skylos/blob/main/docs/privacy-and-network.md).

## Do I Need A Key To Pass The Gate?

No. A token only lets you upload. The gate passes when the issues that fail it
are fixed. On the Workspace and Enterprise plans, a workspace admin or owner can
override a failed gate in Skylos Cloud (Merge anyway); they must give a reason, and it is
recorded with the scan.

## Use Local Only vs Add Cloud

| If you want... | Use this |
|---|---|
| Local scan only | `skylos .` |
| Local security, secrets, quality, and AI-defect checks | `skylos . --danger --secrets --quality --ai-defects` |
| Local exit-code enforcement only | `skylos . --gate` |
| Upload a scan and see this branch's gate | `skylos cloud` |
| Switch this repo to another cloud project | `skylos login` |
| Upload only some checks | `skylos cloud --danger --secrets` |
| Compare Skylos with an existing scanner without replacing its gate | `skylos compare . --against incumbent.sarif --upload` |
| Pull project policy and suppressions into the repo | `skylos sync pull` |
| Inspect which project this repo is linked to | `skylos project status` |

Stay local when you only need a fast developer or CI scan.

Add the cloud when you need:
- scan history
- shared suppressions
- project policy managed in the dashboard
- issues and exception workflows
- trends across branches and time
- GitHub-native features such as OIDC, the GitHub App, deep links, or PR checks

## What Cloud Adds

### Workspace Views

Skylos Cloud currently gives you workspace-level navigation for:
- `Overview`
- `Projects`
- `Scans`
- `Issues`
- `Exceptions`
- `Rules`
- `Trends`
- `Supply chain`: packages your branches use that were later reported as malware, each repository's install protections, and the [exposure map](#supply-chain-exposure-map) for an alert. See [Supply Chain](/supply-chain#in-skylos-cloud).

### Project Views

Each project currently has tabs for:
- `Overview`
- `Scans`
- `Issues`
- `Suppressions`
- `Defense`
- `Provenance`
- `Scanner proof`
- `Settings`

The **Scanner proof** tab stores bounded, tamper-evident comparison receipts from `skylos compare --upload`. Use it to evaluate Skylos beside an incumbent scanner on the same revision before changing a required gate. See [Scanner Comparison](/scanner-comparison).

### Project Settings

`Dashboard -> Settings` is the project-management surface for:
- repository URL
- API key rotation
- GitHub App installation
- Slack and Discord notifications
- team members
- workspace/project policy
- policy inheritance

### Enterprise Trust Controls

Skylos Cloud also provides the current trust foundations needed for a security-team pilot:

- role-based workspace access
- project API keys and GitHub OIDC upload paths
- server-side upload attribution
- audit events for mutating governance workflows
- audit export foundations
- project policy and suppression governance

For the full buyer-facing view, including what exists today and what remains on the enterprise roadmap, see [Enterprise Trust](/enterprise-trust).

### Supply-Chain Exposure Map

When a package version your branches use is reported as malware, the
exposure map shows what it could have reached and what to do first. It
needs the Workspace or Enterprise plan. Malware alerts themselves appear on
every plan; on Free the alert says the map needs the Workspace plan.

Open it from the `Supply chain` page:

- **From an alert:** `Show what it reached and what to rotate` on an open
  alert, or `What it reached` on a resolved one. Alert webhooks
  (`dependency.malicious_detected`) carry an `exposure_url` link to the map.
- **For a report that is not in the feed yet:** open
  `Check a package or GitHub Action that is not in the feed yet`, choose a
  package (npm or PyPI, name and exact version) or a GitHub Action (name and
  ref), and click `Map exposure`.

The map is built from what your uploads sent: each branch's package list,
its CI job list (`ci_inventory`) and its agent hooks (`agent_hooks`). Upload
with dependency checks on (`skylos cloud` or `skylos . -a --upload`) so
those blocks are there.

| Section | What it shows |
|---|---|
| Read before acting | A lockfile entry is not proof of install; developer machines are not covered (the map reads CI uploads only); commits that were never uploaded are blind spots; feeds can be wrong. History starts at the first upload after the exposure map became available, so earlier commits are not covered |
| What to do, in this order | 1. Isolate self-hosted runners and machines. 2. Remove persistence: agent and editor hooks and MCP servers on uploaded branches, and the version itself. 3. Revoke exposed tokens, only after steps 1 and 2, because some 2026 worms wipe the machine when their stolen GitHub token is revoked. 4. Rotate secrets, most privileged first. 5. Check registry publishes made with those credentials. 6. Re-run `skylos . -a --upload` on each branch |
| Where it was (proven) | Branches whose uploaded lockfile had the version: first seen, last seen, the upload before it (or "none (blind spot)"), and whether it is still in the lockfile |
| CI jobs at those commits (inferred) | **Could have installed it:** npm jobs that install from the lockfile with install scripts on, Python jobs that install from the lockfile (`.pth` files and import-time code run without install scripts), or, for a GitHub Action, every job that uses that ref. **Lower risk:** installs with scripts off, tool installs not from the lockfile, a restored cache, a called workflow, or push runs limited to other branches. **No install:** jobs that only ran at the same commits. Each job shows its runner (GitHub-hosted, GitLab runner or self-hosted) and the upload its job list came from |
| Credentials | What those jobs could read, grouped as all secrets, publish, cloud, GitHub and other: `secrets: inherit` or `toJSON(secrets)`, OIDC roles (`id-token: write`), named secrets (names only; values are never uploaded), environment secrets and self-hosted runners |
| Workflow runs in the window (observed) | GitHub Actions runs of those workflows on those branches, marked when they ran at a commit whose lockfile had the version. Listing runs needs the Skylos GitHub App with `Actions: read`; without it, every run in the window counts as possible, never as safe |
| Gaps and blind spots | Evidence Skylos could not see, such as deleted runs, branches never uploaded, missing or partial job lists, reusable workflows from other repositories, and runs past GitHub's retention (90 days by default). Treat each gap as possibly exposed |

`Download Markdown` and `Download CSV` export the whole map for an incident
ticket. When OSV withdraws every advisory behind an alert, the alert closes
as "advisory withdrawn" and its map is cleared: there is nothing to rotate
for that report. An alert also closes once a complete package list from the
branch no longer has the version.

## How the Cloud Fits the CLI

```mermaid
flowchart LR
    A[Run skylos . locally] --> B[skylos cloud]
    B --> C[First run only: log in and pick the project]
    C --> D[Skylos Cloud stores scan and evaluates gate]
    D --> E[Review scans, issues, exceptions, rules, trends]
    E --> F[Change policy or suppressions in dashboard]
    F --> G[skylos sync pull]
    G --> H[Repo gets .skylos/config.yaml and .skylos/suppressions.json]
```

The split is simple:
- **CLI:** analysis happens here
- **Cloud:** history, policy, suppressions, grouping, and team workflows happen here

## Repo URL: Optional vs Required

A project can stay cloud-only and still accept normal API-key uploads.

Set the project `repo_url` when you want:
- GitHub Actions OIDC uploads
- GitHub App installation
- GitHub deep links in the dashboard
- PR-linked GitHub check runs or comments
- repo-aware default-branch behavior

That distinction matters. Basic uploads do **not** require a GitHub repo binding. GitHub-native automation does.

## What Data Gets Sent

When you upload a scan with `skylos cloud` or `--upload`, Skylos Cloud receives analysis results and metadata, not your repository contents.

| Sent | Not sent |
|---|---|
| finding details | source code files |
| file paths | full repository contents |
| line numbers | secrets from your environment |
| code snippets of up to 7 lines (none for secrets) | your `.env` files as raw uploads |
| branch / commit metadata | your git history as source blobs |
| git author email of each flagged line | |
| a map of your functions and classes (names, files, lines, sizes, which calls which) | |
| summary counts and gate data | |
| with dependency checks on: each package's ecosystem, name, version, direct/dev flag and manifest path, plus the supply-chain posture checks | |
| with dependency checks on: each CI job's triggers, runner, permissions, secret names (never values), installs, download hosts (never full URLs) and publish steps, and committed agent hooks and MCP servers with commands redacted | |

Uploaded findings can include security-sensitive metadata and contextual evidence needed to explain results. Treat cloud scan results as sensitive security data even though Skylos does not upload the full repo as source blobs during normal scan upload.

Scanner-comparison receipts are narrower than normal scan uploads: scanner messages, source snippets, fingerprints, and absolute local paths remain local. Cloud receives aggregate evidence and repository-relative review metadata only.
