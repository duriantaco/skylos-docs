Skylos uses LiteLLM as its LLM gateway, giving you one interface across cloud and local providers (OpenAI-compatible APIs). You can use OpenAI, Anthropic, Google, Mistral, Groq, xAI, Together, DeepSeek, and local runtimes like Ollama / LM Studio / vLLM by changing the model name and (optionally) the base URL—without changing Skylos code.

The `skylos agent ...` commands need the `llm` extra:

```bash
pip install "skylos[llm]"
```

`skylos verify`, `skylos defend` and every normal scan do not use an LLM.

## Architecture Overview

Skylos uses a **hybrid analysis approach** that combines the strengths of both static analysis and LLMs:

```
┌─────────────────────┐         ┌─────────────────────┐
│   Static Analysis   │         │    LLM Analysis     │
│   (Deterministic)   │         │  (Context-Aware)    │
│                     │         │                     │
│  • Fast & Free      │         │  • Logic bugs       │
│  • Pattern matching │         │  • Understands      │
│  • AST-based        │         │    intent           │
│  • No hallucinations│         │  • Explains issues  │
└──────────┬──────────┘         └──────────┬──────────┘
           │                               │
           └───────────┬───────────────────┘
                       ▼
            ┌─────────────────────┐
            │   Merge & Classify  │
            │                     │
            │  Both found → HIGH  │
            │  Static only → MED  │
            │  LLM only → MED,    │
            │    needs review     │
            └─────────────────────┘
```

This approach catches more issues than either method alone while maintaining high confidence through cross-validation.

## Why Hybrid Analysis (And Why LLMs Alone Are Not Enough)

LLMs are powerful at understanding *intent* — but they are **not reliable static analyzers**.

Static analysis is deterministic and rule-based. LLMs are probabilistic and can behave differently across runs. That means an LLM-only scanner can miss real issues or invent issues that don’t exist.

### What LLMs are bad at (and why Skylos doesn’t rely on them alone)

LLMs struggle with:

- **Determinism:** the same file may produce different results across runs, temperatures, or providers  
- **Completeness:** token limits force truncation → the model may miss code paths or entire files
- **Precision:** models sometimes report issues that sound plausible but are not actually present
- **Exactness:** line numbers, symbol names, call graphs, and imports can be wrong
- **Large codebases:** cross-file reasoning is limited by context size and missing definitions
- **Ground truth guarantees:** an LLM cannot prove reachability, data flow, or exploitability

Because of these limitations, Skylos uses static analysis as the **truth layer** and uses LLMs to provide **contextual reasoning and remediation suggestions**, not as the source of truth.

**Best practice:** Treat LLM findings as a *review layer*, not a final verdict.


## Setup

### API Key Configuration

Skylos resolves API keys per provider:

1. Environment variables (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, `GEMINI_API_KEY`, `MISTRAL_API_KEY`, `GROQ_API_KEY`, `XAI_API_KEY`, `TOGETHER_API_KEY`, `DEEPSEEK_API_KEY`)
2. Keys saved with `skylos key` (stored in the system keyring)
3. Interactive prompt (only if allowed and no key is found)

```bash
skylos key                      # menu (needs a terminal)
skylos key list                 # which providers have a saved key
skylos key add openai           # save a key for one provider
skylos key remove openai        # delete a saved key
```

```bash
# OpenAI
export OPENAI_API_KEY="sk-..."

# Anthropic
export ANTHROPIC_API_KEY="sk-ant-..."
```

Keys entered interactively are saved to your system keyring for future use.

### Local LLM Configuration (Ollama / LM Studio / vLLM)

For local LLMs, an API key is usually not required (depends on how your local server is configured). Set the base URL:

```bash
# Ollama
export SKYLOS_LLM_BASE_URL="http://localhost:11434/v1"

# LM Studio
export SKYLOS_LLM_BASE_URL="http://localhost:1234/v1"

# vLLM
export SKYLOS_LLM_BASE_URL="http://localhost:8000/v1"
```

Or pass it directly via CLI:

```bash
skylos agent scan . --base-url http://localhost:11434/v1 --model qwen2.5-coder:7b
```

### Provider Selection

Skylos automatically detects the provider from the model name, or you can force it:

```bash
# Auto-detect (default)
skylos agent scan . --model gpt-4.1
skylos agent scan . --model claude-sonnet-4-20250514

# Force provider explicitly
skylos agent scan . --provider openai --model my-custom-model
skylos agent scan . --provider anthropic --model my-custom-model
```

:::note
If you force a provider, make sure the model name is valid for that provider/base URL.
:::

Environment variable alternative:

```bash
export SKYLOS_LLM_PROVIDER=openai
export SKYLOS_LLM_BASE_URL=http://localhost:11434/v1
```

## Commands

### `skylos verify`

Run the focused source verifier for code an agent or editor is working on:

```bash
skylos verify . --file src/app.py --range 40:75 --project-context
```

When a repository has local generated-code truth, create an AI hallucination
contract and apply it during verification:

```bash
skylos contract init
skylos verify . --contract .skylos/ai-contract.yml
skylos verify . --file apps/api/routes.py --project-context --contract .skylos/ai-contract.yml
```

`skylos verify` is different from a full scan. For a directory target, its
AI-code analysis covers the selected tree. A separate Python-only `behavior`
result compares supported working-tree functions with Git HEAD; that behavior
model does not restrict every analyzer finding to changed files. Findings can
include hallucinated references, unfinished generated code, stale references,
disabled controls, dependency hallucinations, API signature hallucinations,
and weakened assertions. Full scan JSON reports the strict AI-defect rules
under `ai_defects` rather than `quality` or `danger`.

Path targets enable dependency hallucination checks by default, which may query
public package registries. Use `--no-dependency-hallucinations` to disable those
lookups. The CLI renders a human report on a terminal and emits the stable JSON
schema when redirected, when `--stdin` is used, or when `--output` selects a
file.

For the full static-scan AI-defect method, category contract, and current rule
list, see [AI Defect Verification](./ai-defects). For repo-specific verifier
contracts, see [AI Hallucination Contracts](./ai-contracts).

Agents and editors can also pass unsaved buffers through stdin:

```bash
printf '{"file":"src/app.py","code":"def handler(): pass\n","range":"1:1"}' \
  | skylos verify . --stdin --no-fail
```

The JSON result uses `tool: "verify_change"` and includes `rule_id`,
`vibe_category`, `ai_likelihood`, `range`, `message`, `suggested_fix`,
`confidence`, `severity`, and `category` for each finding. Contract-backed
findings may also include `contract_id`, `contract_clause`, `contract_path`,
and `contract_reason`. Without `--no-fail`, the command exits `1` when the
verifier returns a failing status.

### MCP `verify_change`

The MCP server exposes the same verifier as `verify_change`, so coding agents can
call Skylos after each edit. The tool accepts `path`, optional `file`,
`line_range`, `project_context`, `confidence`, `contract_path`, and
`include_dependency_hallucinations`, then returns the same versioned JSON schema
as the CLI.

Use `verify_change` when you want an agent to self-correct before a human review
sees a hallucinated helper, stale reference, disabled control, or invented API
call.

### `skylos agent scan`

Run hybrid AI-powered analysis with full project context:

```bash
skylos agent scan ./src
```

**How it works:**

1. Runs static analysis first to build project context (`defs_map`)
2. Passes the context to LLM agents for deeper analysis
3. Merges findings and assigns confidence scores
4. Detects issues static analysis can't: logic bugs, hallucinated function calls, business logic flaws

**Options:**

| Flag | Description |
|------|-------------|
| `--model` | Model to use (default: `gpt-4.1`) |
| `--provider` | Force provider: `openai`, `anthropic`, `google`, `mistral`, `groq`, `xai`, `together`, `deepseek` or `ollama` |
| `--base-url` | Custom endpoint for local LLMs |
| `--format` | Output format: `table`, `tree`, `json`, `sarif` |
| `--output`, `-o` | Write output to file |
| `--min-confidence` | Filter by confidence: `high`, `medium`, `low` |
| `--with-fixes` | Generate fix suggestions without applying them |
| `--llm-only` | Skip static analysis and run the LLM only |
| `--changed` | Analyze only git-changed files |
| `--verify-dead-code` | Run the slower LLM dead-code check before showing results |
| `--prompt-template KIND=PATH` | Append a trusted prompt file. KIND is `security`, `quality`, `security_audit` or `review`. Repeatable |
| `--strict` | Exit with an error when findings are reported |
| `--upload` | Send findings and the run summary to Skylos Cloud (off by default) |

**Examples:**

```bash
# Basic analysis
skylos agent scan ./src

# With local Ollama
skylos agent scan ./src \
  --provider openai \
  --base-url http://localhost:11434/v1 \
  --model codellama:13b

# Generate suggestions without changing files
skylos agent scan ./src --with-fixes

# Preview the separate remediation workflow
skylos agent remediate ./src --dry-run

# Output as SARIF for CI integration
skylos agent scan ./src --format sarif --output results.sarif
```

### `skylos agent scan --security`

Security-only taskflow audit for repo-aware vulnerability review:

```bash
skylos agent scan . --security
```

**How it works:**

1. Builds a repo map from the activation index and discovered Python files
2. Derives framework-aware file facts such as user-controlled sources, dangerous sinks, and guards/sanitizers
3. Runs whole-file security review with those facts in prompt context
4. Re-verifies surviving findings and records evidence such as `hypothesis`, `review_supported`, and `refuted`
5. Emits findings in `table`, `tree`, `json`, or `sarif` output formats

**Options:**

| Flag | Description |
|------|-------------|
| `--model` | Model to use (default: `gpt-4.1`) |
| `--provider` | Force provider, as for `agent scan` |
| `--base-url` | Custom endpoint for local LLMs |
| `--format` | Output format: `table`, `tree`, `json`, `sarif` |
| `--output`, `-o` | Write output to file |
| `--interactive`, `-i` | Optional interactive file selection before the audit |

`skylos agent security-quick [path]` is the same command.

For a longer, resumable audit (threat model, candidates, LLM validation and
exports), use `skylos agent security-deep [path]` (also `skylos agent audit
--deep`). `--scan-only` runs its static stage with no LLM.

**Why use it:**

- richer repo context than a single-file prompt
- framework-aware hints for Flask, FastAPI, and Django-style handlers
- verifier-backed evidence instead of a single opaque model verdict
- a candidate ledger that keeps finding identity and stage transitions stable internally

**Example output:**

```json
{
  "findings": [
    {
      "rule_id": "SKY-D216",
      "severity": "critical",
      "message": "Possible SSRF: tainted URL passed to HTTP client.",
      "location": {
        "file": "app.py",
        "line": 10
      },
      "symbol": "proxy",
      "metadata": {
        "security_evidence": "review_supported",
        "review_verdict": "SUPPORTED",
        "review_reason": "challenge pass resolved the SSRF flow"
      }
    }
  ],
  "summary": "Found 1 issues: 1 critical"
}
```

The same run also writes `.skylos/runs/<run-id>/repo_map.json`, `candidates.json`, `verified.json`, and `summary.json`.

### `skylos agent remediate`

Scan a path, fix findings with an LLM, and optionally test and open a PR:

```bash
skylos agent remediate ./src --dry-run           # show what would be fixed
skylos agent remediate ./src --severity high     # fix high and critical only
```

**Options:**

| Flag | Description |
|------|-------------|
| `--max-fixes` | Maximum number of findings to fix (default: 10) |
| `--dry-run` | Show what would be fixed without changing files |
| `--severity` | Only fix findings at or above `critical`, `high`, `medium` or `low` |
| `--test-cmd` | Trusted test command to run after fixes (no shell) |
| `--auto-test` | Run auto-detected project tests after fixes |
| `--auto-pr` | Create a PR with the fixes |
| `--branch-prefix` | Git branch prefix for that PR |
| `--standards [FILE]` | LLM-guided cleanup mode, optionally with your standards `.md` file |
| `--model`, `--provider`, `--base-url` | Model settings, as for `agent scan` |
| `--upload` | Send the run summary to Skylos Cloud (off by default) |

Skylos runs tests after a fix only when you pass `--auto-test` or `--test-cmd`.
For supported security findings, Skylos also re-runs the relevant analysis after
a fix to confirm the original finding is closed. For `SKY-D211` SQL injection findings, Skylos
can also generate a targeted regression-test candidate and include proof
metadata in the remediation summary.

Regression proof metadata includes:

- `rule_id`
- `family`
- `source_file`
- `test_file`
- `description`

### `skylos agent scan --changed`

Scan only git-changed files:

```bash
skylos agent scan --changed
```

This is a convenience flag that:
1. Finds files changed in git
2. Runs analysis only on those files
3. Fits pre-commit or PR review workflows

## Applying AI Remediation

`skylos agent scan --with-fixes` produces suggestions. Use the explicit
remediation command when you intend to change files:

```bash
skylos agent remediate . --dry-run
skylos agent remediate .
```

Add `--auto-test` only for a trusted repository, or pass a trusted command with
`--test-cmd`. PR creation is opt-in with `--auto-pr`.

## What Gets Detected

### Static Analysis Finds

- Unused functions, imports, variables, classes
- Security patterns (SQL injection, command injection, XSS)
- Code quality issues (complexity, nesting depth)
- Hardcoded secrets

### LLM Analysis Adds

- **Logic bugs:** Off-by-one errors, incorrect conditions, missing edge cases
- **Hallucinations:** Calls to functions that don't exist in your codebase
- **Business logic flaws:** Authentication bypasses, broken access control
- **Context-dependent issues:** Problems that require understanding intent

### In-Loop Verifier Adds

- **Machine-stable output:** a small JSON verdict shaped for agents, not a full human report
- **Range filtering:** findings can be scoped to the lines an agent just edited
- **Real API checks:** Python package calls can be checked against installed API surfaces
- **Dependency checks:** Python imports and package manifest pins can be checked against registry metadata; raw diffs that add both an import and its manifest declaration are handled together
- **Local operation:** verifier findings come from Skylos analysis; LLM use is not required

### Confidence Scoring

Findings are scored based on source:

| Source | Confidence | Meaning |
|--------|------------|---------|
| Static + LLM agree | **HIGH** | Very likely a real issue |
| Static only | **MEDIUM** | Deterministic match |
| LLM only | **MEDIUM** | Marked as needing human review |

3. Start the local server (default port: 1234)

## Configuration

LLM settings come from flags and environment variables, not from
`pyproject.toml`. Set the model with `--model`, the provider with
`--provider`, and a local endpoint with `--base-url`.

To add your own prompt text, pass `--prompt-template KIND=PATH`. A
`[tool.skylos.templates]` table in config is not read.

### Environment Variables

| Variable | Description |
|----------|-------------|
| `OPENAI_API_KEY` | OpenAI API key |
| `ANTHROPIC_API_KEY` | Anthropic API key |
| `GEMINI_API_KEY`, `MISTRAL_API_KEY`, `GROQ_API_KEY`, `XAI_API_KEY`, `TOGETHER_API_KEY`, `DEEPSEEK_API_KEY` | Other provider keys |
| `SKYLOS_LLM_PROVIDER` | Force provider, for example `openai` or `anthropic` |
| `SKYLOS_LLM_BASE_URL` | Custom base URL for OpenAI-compatible APIs |
| `OPENAI_BASE_URL` | Alternative to `SKYLOS_LLM_BASE_URL` |

## Best Practices

### For Analysis

1. **Use `skylos agent scan`** for full project context
2. **Start with static analysis** (`skylos .`) to see baseline findings for free
3. **Review LLM-only findings carefully** — they may need validation
4. **Trust HIGH confidence findings** — both engines agree

### For Fixes

1. **Never blindly apply fixes** — always review the diff
2. **Run tests after applying** — verify functionality
3. **Check remediation proof** — for security fixes, confirm the finding was re-scanned as closed
4. **Fix incrementally** — one category at a time

### For AI-Code Defect Benchmarks

Skylos includes a checked-in benchmark harness for AI-code defect cases:

```bash
python scripts/ai_code_defect_benchmark.py
python scripts/ai_code_defect_benchmark.py --json
python scripts/ai_code_defect_benchmark.py --case dependency-version-hallucination
```

The benchmark exercises the verifier against curated AI-defect fixtures and
reports score, recall, absence-guard results, and failures. Use it when changing
AI-defect rules, verifier filtering, package hallucination detection,
signature validation, assertion-weakening detection, and diff-aware PR
verification rules.

### For CI/CD

```yaml
# GitHub Actions example
- name: Skylos Security Scan
  run: |
    skylos agent scan ./src \
      --format sarif \
      --output skylos-results.sarif \
      --min-confidence high

- name: Upload SARIF
  uses: github/codeql-action/upload-sarif@v3
  with:
    sarif_file: skylos-results.sarif
```

## Troubleshooting

### "No API key found"

For cloud providers:
```bash
export OPENAI_API_KEY="sk-..."
# or
export ANTHROPIC_API_KEY="sk-ant-..."
```

For local LLMs, ensure `--base-url` points to your server (and provide a key only if your server requires one):
```bash
skylos agent scan . --base-url http://localhost:11434/v1 --model qwen2.5-coder:7b
```

### "Connection refused" (local LLM)

1. Verify your LLM server is running:
   ```bash
   curl http://localhost:11434/v1/models  # Ollama
   curl http://localhost:1234/v1/models   # LM Studio
   ```
2. Check the port matches your `--base-url`

### "Model not found"

- **Cloud:** Verify your API key has access to the model
- **Ollama:** Run `ollama pull <model-name>` first
- **LM Studio:** Load the model in the UI before using

### High costs

- Use `--min-confidence high` to reduce output noise
- Use `skylos agent scan --changed` to analyze only changed files
- Switch to local LLMs for development iteration
- Use smaller models (e.g., `gpt-4o-mini`, `claude-haiku`)

### Slow responses

- Use local LLMs with GPU acceleration
- Reduce file count with `--changed`, or pick files with `--security -i`
