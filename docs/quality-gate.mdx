## Local gate and Cloud gate

The local CLI gate evaluates the findings in the scan against your configured
limits and returns an exit status. Skylos Cloud applies project policy to
uploaded findings and can publish a GitHub check. These are separate decisions.

A local full scan counts existing findings too. To gate a change, choose
`--diff` or `--baseline` explicitly. Cloud's `zero-new` policy evaluates new,
unsuppressed findings against its baseline; see [Project Policy](/project-policy).

## Run the local gate

```bash
pip install skylos
skylos . --danger --secrets --quality --ai-defects --gate
```

`--gate` evaluates the analyzers enabled in that invocation. It does not enable
every analyzer by itself. `-a` enables the full scan, including dependency CVEs;
dependency checks can query public registries and OSV.

In noninteractive use, an exceeded limit returns exit `1`. An incomplete scan
returns exit `2`, including when `--force` is present. Passing the finding gate
means the findings are within its limits; it does not mean there are no findings.

### Configuration

Configure the local limits in `pyproject.toml`:

```toml
[tool.skylos.gate]
fail_on_critical = true
max_critical = 0
max_high = 5
max_security = 10
max_quality = 10
max_ai_defects = 10
max_secrets = 0
max_dependency_vulnerabilities = 0
max_reliability = 0
strict = false
# max_dead_code = 0             # opt in; no dead-code count limit by default
```

These are the standard count limits. A count equal to its limit passes; a count
above the limit fails. For example, three HIGH security findings can pass
`max_high = 5`, provided no other limit is exceeded. Set `max_high = 0` to block
any HIGH security finding. `max_security` counts all security findings, not only
HIGH ones. Separate limits apply to secrets, quality, AI defects, dependency
vulnerabilities and reliability. If `max_ai_defects` is omitted, it uses
`max_quality`. Quality rules designated as advisory remain report-only.

## Gate changed lines

For a pull request, fetch the base reference and scan the changed lines:

```bash
git fetch origin main
skylos . --danger --secrets --quality --ai-defects --diff origin/main --gate
```

Use your repository's default branch if it is not `main`. Findings outside the
selected diff are filtered out; this is useful when existing debt should not
block a new change. `--diff-base origin/main` instead selects whole changed
files. Neither option establishes that the unchanged code is safe.

## Gate only new findings with a baseline

Record the findings you have already reviewed, then use that baseline on later
scans:

```bash
skylos baseline .
skylos . --danger --secrets --quality --ai-defects --baseline --gate
```

`skylos baseline .` records existing findings in `.skylos/baseline.json`.
`--baseline` filters matching findings from subsequent scans. New findings still
count against the gate limits. To include dependency CVEs in the saved baseline,
use `skylos baseline . --sca` and enable `--sca` on subsequent scans.

Treat the baseline as a reviewed policy input. Replacing it with the current
findings can hide the very regression you intended to block. A local baseline
and a Cloud baseline are separate.

## Strict mode and force

`--strict` fails when gate-relevant findings remain, regardless of the count
limits. In the terminal it also disables the interactive offer to continue
past a failed gate:

```bash
skylos . --danger --secrets --quality --ai-defects --strict
```

`--force` explicitly bypasses the local finding-gate failure, even alongside
`--strict`. This behavior is the same on Free, Workspace and Enterprise. A
paid plan does not turn the local CLI into a control an agent cannot bypass.
An incomplete scan still exits `2`.

Use a required CI check to enforce the reviewed command and protect the workflow
and configuration that define it. See [Your First Gated PR](/first-gated-pr).

## Release Reliability Gates

Reliability has an independent threshold, `max_reliability`, which defaults to
`0`. It does not consume `max_security` or alter the Security count. `--danger`
enables deployment/runtime contract analysis as well as Security; exact
`--select` rules enable the analyzer families they need.

```bash
# Check the external Kubernetes deployment path
skylos . --select SKY-DEP001,SKY-DEP002,SKY-DEP003 --gate

# Check GPU source/build intent against the declared target fleet
skylos . --select SKY-GPU001,SKY-GPU002,SKY-GPU003 --gate
```

The GPU gate retains `SKY-GPU000`. A missing, invalid, deleted or incomplete
required GPU contract blocks. See [Release Reliability](/release-reliability)
for setup.

That rule gate does not inspect a built binary. After the build, run
`skylos preflight build/app`; its independent contract returns `0` for `PASS`,
`1` for a proved incompatibility, and `2` for `UNKNOWN` or invalid input.

## Cloud governance and required checks

Connect a project to Skylos Cloud when you want a shared baseline, persistent
review decisions and GitHub checks. Cloud's gate modes are:

| Mode | Blocks when |
|:---|:---|
| `zero-new` | Any new, unsuppressed finding remains |
| `category` | A new-finding count exceeds a category limit |
| `severity` | A new-finding count exceeds a severity limit |
| `both` | Either category or severity limits are exceeded |

Free supports `zero-new`; Workspace and Enterprise support advanced modes.
Free also supports PR checks and up to 25 suppressions per project. Workspace
and Enterprise add audited overrides and other governance features; see
[Billing & Credits](/billing) and [Project Policy](/project-policy).

An authorized reviewer can record a decision on a finding or, where policy and
permissions allow it, override a failed scan with a reason. Cloud recomputes its
verdict and updates an eligible GitHub check. Other policy requirements can
still block the check. The CLI does not wait for approval or resume a deployment
when the dashboard decision changes.

For enforcement, require the intended GitHub check in a branch ruleset and
review who can bypass that ruleset. A local `--force` is not a Cloud override,
and a laptop upload does not establish a Cloud-verified GitHub check. See
[Authentication](/authentication) for upload attribution and
[Your First Gated PR](/first-gated-pr) for setup.

## CI example

The simplest setup is `skylos cicd init --no-upload`, which generates a
pull-request Quality Gate and adds Done when it discovers your tests. Require
those checks in GitHub; adding the workflow alone does not make them required.

For an existing workflow, run the gate before dependent steps:

```yaml
- name: Skylos Quality Gate
  run: skylos . --danger --secrets --quality --ai-defects --diff origin/main --gate
```

Fetch the base reference first and use full checkout history as shown in the
[first gated PR guide](/first-gated-pr). Avoid `--force`, `|| true` and
`continue-on-error` in an enforcing job. Pin the verifier and protect the
workflow. The Cloud-upload job is optional and has separate setup requirements.
